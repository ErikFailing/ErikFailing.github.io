Three times during the GameNetworkingSockets fuzzing I had something that looked like a real
finding and turned out to be my own harness or build. One of them I'd even written down as
confirmed. None of them got reported, because my rule was that {=point: nothing goes to a vendor
until I understand its root cause=}. This post is those three, and the checks I'd run on any
crash now.

## Why This Matters More Than Finding Bugs

{=point: A fuzzer crash is a claim=}, and the fuzzer isn't the one who has to stand behind it. If
I send Valve a report and their engineer spends an hour discovering that my test harness built an
impossible situation, I've wasted their time and they'll read my next report a little more
skeptically. I think the honest version of fuzzing is {=static: mostly triage=}, and most of what
you triage early on is yourself.

## False Positive 1: Uninitialized Memory On The Wire

This is the one that got me. MemorySanitizer (MSan) reported that GNS was sending {=glitch:
uninitialized memory in a handshake packet=}: 128 of the 217 bytes in a connect request, flagged
right at the `sendto` call. It looked like a {=crimson: textbook information leak=}, and
everything I checked seemed to agree:

- It was deterministic.
- It reproduced with encryption on and off.
- The function that sends the packet doesn't zero its buffer first, and a sibling function does.

So I recorded it as a confirmed finding. That lasted less than a day, until I traced where the
128 bytes actually came from:

- 32 bytes: the certificate's public key
- 32 bytes: the ephemeral key-exchange key
- 64 bytes: the signature over the session crypto info

{=trophy: 32 + 32 + 64 = 128=}. Exactly the flagged bytes, with nothing left over. And all three
are generated by {=arcane: OpenSSL=}, which my MSan build hadn't instrumented. {=point: MSan can
only track memory written by code it compiled=}, so anything an uninstrumented library writes
looks uninitialized, even a freshly generated key.

Two more checks made it airtight. Right after generation, each key was already flagged from byte
0, which can only happen if MSan never saw it being written. And when I told MSan to treat just
those three OpenSSL outputs as initialized, the packet went out with {=ward: zero flagged bytes=}.

Looking back, my "confirmations" never tested the right thing. Encrypted mode generates its
keys with OpenSSL too, so of course it reproduced there. And the missing `memset` was real but
irrelevant: that function sends exactly the serialized message, with no padding to leak.

The fix was the expensive option I'd been putting off: build OpenSSL from source under MSan
too, next to the already-instrumented libc++ and protobuf, so {=iron: the whole dependency stack
is instrumented=}. After that the
harnesses replay their full corpora with no MSan reports at all.

## False Positive 2: A Crash In My Own Stand-In

This one was quick. One of the stateful harnesses crashed on a null socket, and the null came
from my harness's stand-in for the network, not from anything the library did with attacker
bytes. I fixed the harness and the crash went away.

It's a boring story, but it's the most common kind. A harness reaches into the middle of a
library and fakes the parts around it, and {=ghostly: every fake is a place to manufacture a crash=}
that no attacker could cause.

## False Positive 3: 439 Crashes, One Bug, Mine

During an overnight campaign I built a new harness for the code that handles acknowledgments
of sent packets (the one from [the stateful fuzzing post](/posts/fuzzing-stateful-code/)). Under
the assert oracle, where GNS's internal invariant checks count as crashes, it {=static: saved 439
crashes in one run=}. For a few minutes that's a very exciting number.

Every one of them was the same assert: the elapsed time between sending a packet and receiving its
ack was negative. The cause was {=glitch: two clocks=}. The harness primed its in-flight packets
using the library's real clock, then delivered the fuzzed acks stamped with a fixed logical clock
that was *earlier* than those sends. So GNS was being handed acks for packets that, as far as it
could tell, {=ghostly: hadn't been sent yet=}, and its assert correctly said that's impossible.

What I checked before believing that explanation:

1) Replayed 8 of the 439 inputs. All 8 hit the identical assert, so it was one bug, not many.
2) Fixed the harness to stamp acks with the real clock, read after priming.
3) Replayed the same 8 inputs on the fixed harness: {=trophy: 0 of 8 crashed=}.
4) Re-ran the campaign: 45 minutes, 14 instances, 21.7 million executions, zero assert
   crashes.

So the real result for that surface is that it held up under both oracles, and the 439 were me
lol. The lesson I took: {=point: an assert oracle is only as good as the harness's consistency=}.
If the harness builds state through one clock, everything it delivers afterward has to live on
that same clock.

## The Tooling Side

A few things in the triage setup exist specifically to keep noise from looking like signal:

- **Deduplicate first.** [CASR](https://github.com/ispras/casr) replays every crash file and
  clusters them by stack, so 470 files become "one distinct crash" before I read anything.
- **Report the real crash site.** For an assert, the crashing frame is my own oracle hook. The
  triage script walks up the stack to the first frame inside GNS and reports that.
- **Don't guess at what doesn't reproduce.** Each crash is replayed once in a fresh process. If it
  only happened because of state built up over thousands of earlier inputs, it's reported as "not
  reproduced", not counted as a finding.
- **Whitelist by location.** Some GNS asserts fire on malformed input by design. Once I've triaged
  one as benign, it goes on a list {=iron: keyed by file and line, not by message text=}, so a
  different assert with similar wording can't hide behind it.

That third point also decided which engine I use for what. AFL++ keeps one process alive across
many inputs, and GNS has a process-wide clock that the per-input connection rebuild doesn't
reset. So an AFL++ assert crash can depend on accumulated clock state and fail to reproduce
alone. I use AFL++ for the memory-safety oracle, where crashes come from the input's content,
and {=static: libFuzzer when an assert crash has to reproduce=}.

## What I Check Now

Overall, I think the checklist from these three is short:

- **Does it reproduce from the one file, in a fresh process?** If not, it's a lead at best.
- **Whose code is at the top of the stack?** The target's, mine, or a library the sanitizer
  can't see into?
- **Could the setup happen in the real world?** An ack from the future can't.
- **Does the explanation account for everything?** 128 flagged bytes that split exactly into
  32 + 32 + 64 is an explanation. "It's probably a leak" wasn't.
- **Would a different experiment have come out differently if I were wrong?** My
  encrypted-mode test couldn't have, so it proved nothing.

I think catching these three mattered more than anything the fuzzers found. I'd rather report
{=point: one thing I fully understand=} than five things I hope are real.
